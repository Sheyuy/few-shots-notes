## 1. p005 · 8 维帽集（Cap set in F₃⁸）

### 1.1 基线复现

```bash
python3 problems/p005-cap-set-8d/verify/verify.py problems/p005-cap-set-8d/baseline
# {"valid":true,"score":"512",...}
```

512 点、F₃⁸、无三点共线。本轮所有搜索都从该证书出发；候选一律用官方 verifier 复核。

### 1.2 饱和性：与其他工具一致的独立复现

对 512 集计算 forbidden 集 `F(S) = {-(a+b) : a,b∈S, a≠b}`：

- `|F(S)| = 6049`，恰好等于外部点数 `6561-512`，因此**没有任何单点可加入**。
- 每个外部点被 **至少 4 条线**阻塞（阻塞线数分布 4..256，中位数量级 20）。
- 随机移除 `r` 个点后，可用候选集大小恰好等于 `r`（只释放被移除的点本身，不释放新点）。

这与仓库 `p005/README.md` 的 `|A|=k` 结论一致，可视为交叉验证。

### 1.3 7 维分层精确模型（本轮新增）

按第一坐标把 F₃⁸ 分成 3 个 7 维层，512 解的分层大小为 **192 / 160 / 160**。

对每一层，固定另外两层，则该层的可行点集合可精确构造；层内“无三线”等价于在候选图上求**最大团**。

结果：

| 层 | 候选集大小 | 当前层大小 | 精确最大团 |
| --- | --- | --- | --- |
| 0 | 200 | 192 | **192** |
| 1 | 229 | 160 | **160** |
| 2 | 229 | 160 | **160** |

**结论：在固定另外两层的条件下，每一层都已达到精确最大。** 单层坐标下降无法改进。

### 1.4 跨层交换与联合重启

- **单点跨层交换**：固定两层，从第三层移除 1 个点，重算候选集并精确求最大团。共 960 次（3 个目标层 × 2 个被移除层 × 全部点），**最好总点数 511**（没有一次回到 512，更没有 513）。
- **两层联合重启**：随机移除层 1/层 2 的 1–4 个点，完整重算两层候选并精确求团，交替优化，300 次，**最好 512**。
- **随机仿射重分层**：对 512 解施加 120 个随机可逆 8×8 仿射变换（over F₃），每次换一个方向重新分层，再做逐层精确优化。**最好 512**。随机变换下最大层大小约 184–190，均未产生 +1。

### 1.5 全局 CP-SAT（本轮重点，仓库“未尝试方向”的落地）

此前仓库把“全局 SAT/CP-SAT 编码 6561 点”列为未尝试方向，原因是约束规模大。本轮实际落地并跑通。

**模型**

- 变量：6561 个布尔变量（每个 F₃⁸ 点是否入选）。
- 约束：F₃⁸ 的全部三点线，每条线 `x_a + x_b + x_c ≤ 2`。
- 线数：`C(6561,2)/3 = 7,173,360`。
- 目标：`maximize Σ x`。
- 求解器：OR-Tools CP-SAT，带 **512 解 hint**（`AddHint`），从已知最优解出发。

**构建与资源实测**

| 阶段 | 数据 |
| --- | --- |
| 生成 7,173,360 条线 | 5.6 s |
| 逐条加入 CP-SAT 约束 | 约 183 s（无其他任务竞争时） |
| presolve 后主模型内存 | 约 77 GB |
| 64 worker 运行时总内存 | 约 116–137 GB |
| 64 worker 时 CPU | 约 26–34 核（受内存带宽限制） |

**关键排错：256 worker 必然 OOM**

- 首次用 `num_search_workers = 256`：模型构建完成后（`model ready`）进入 Solve 即被杀，管理器每约 11 分钟重启一次，整夜共 9 次，**没有一次进入稳定搜索**。
- 根因：CP-SAT 多 worker 会复制/展开大模型，7M 级约束下 256 份直接打爆内存。
- 修复：`num_search_workers = 64`，内存稳定在 137 GB 以内，可长期运行。
- 结论给后来者：**这种 7M 约束的 CP-SAT 模型，worker 数不要按核数给，按内存给**。

**运行结果（6 小时预算结束）**

- 实例 A（64 worker）：`status FEASIBLE obj 512, wall 21635.9 s`，保存 512 点。
- 实例 B（32 worker、`random_seed=12345`）：`status FEASIBLE obj 512, wall 21653.5 s`，保存 512 点。
- 两个证书都用官方 verifier 复核：`{"valid":true,"score":"512","canonical_hash":"f76ee04c31a60fb0ee33ab5dc5d99191dfe19b6384a5a88e696287b103e72e6e"}`，**与 baseline 完全相同**。
- **结论**：6 小时预算内没有找到 513；状态是 `FEASIBLE` 而不是 `OPTIMAL`，因此**不等于证明 513 不存在**，只说明这段算力没找到。

**复现**

```bash
pip install ortools==9.11.4210   # aarch64 需该版本；最新版无 aarch64 wheel
python3 src/codearts/p005/global_cpsat_hint.py
# 需要 /workspace/p005/baseline.json（512 点，JSON: {"points": [[...8 个 0..2], ...]}）
```

### 1.6 p005 小结

- 局部：512 是极强局部最优，单层/跨层/仿射重分层全部回到 512。
- 全局：CP-SAT 已跑通，64 worker 是安全配置；6 小时预算内两个实例均返回 `FEASIBLE 512`（未证明最优），证书与 baseline 相同。
- 给后来者：**不要再从 512 出发做局部变换**；要么全局 CP-SAT 长跑，要么换全新构造（FunSearch 式进化、7 维 236 点 cap 的分层构造等）。

### 1.7 后续否证：对称破缺与 171/171/171 分层（2026-10-30 补）

**A. 标准点对称破缺无效**

理论上，任何 513 点 cap 的仿射秩必为 8（若落在 7 维仿射子空间，大小受 cap(7) 限制，远小于 513）。因此平移 + GL(8,3) 后可 WLOG 让解包含 `0, e1, …, e8` 共 9 个标准点。模型加这 9 个 `x=1` 是严格有效的。

实测：

- 固定 9 个标准点后，剩余可行候选集 `|C| = 6516`（仅排除了 45 个共线点），**候选空间几乎没有缩小**。
- 小维度对照（d=6，已知 cap(6)=112）：
  - 无破缺、600 秒：`FEASIBLE 92`；
  - 有破缺、600 秒：`FEASIBLE 83`。
  - 两者都远低于 112。
- 结论：**CP-SAT 本身在这个最大帽集问题上搜索效率很低**，对称破缺只减少对称副本，不是瓶颈；不要再把“加对称破缺”当作提速手段。

**B. 171/171/171 分层路线不可行**

512 解的分层是 192/160/160。一个自然想法是把层 0 删到 171，让层 1/2 各补 11 点，得到 171×3 = 513。

实测（随机把层 0 删到 171）：

- 层 1/2 的候选集**仍然是 229**（删掉层 0 的 21 点没有释放任何新的层 1/2 候选）；
- 而在这 229 个候选上，层 1/2 的精确最大团只有 **160 + 160 = 320**（此前已精确证明）；
- 因此该结构最多 `171 + 320 = 491`，**远不可能到 513**。

**给后来者的结论**：p005 在“固定分层 + CP-SAT + 局部变换”这套工具下已基本封死。若要继续，需要 FunSearch 式程序进化、更强的专用最大独立集求解器，或彻底不同的代数构造。

## 2. p001 · 11 维接吻数（Kissing number in dimension 11）

### 2.1 基线结构

604 个向量的坐标全部是 `p + q√2`，且每个坐标只取纯形式（`(p,0)` 或 `(0,q)`）：

- 480 个：4 个 `±3` 的整数坐标（其余 0）；
- 96 个：2 个 `±3` + 3 个 `(±1,±2,±2)√2`；
- 16 个：单个 `±6`；
- 6 + 6 个：纯 √2 形式 `(1,1,4)` 与 `(3,3)`。

所有向量平方长度 36，两两内积 ≤ 18。

### 2.2 纯形态候选枚举（本轮新增）

在 5 类纯形态族中枚举全部 norm²=36 候选（共约 46 万）：

| 族 | 候选数 | 合法（可加入） |
| --- | --- | --- |
| 4×±3 | 5,280 | 0 |
| 单 ±6 | 22 | 0 |
| 2×±3 + (1,2,2)√2 | 443,520 | 0 |
| 2×±3 + (3)√2 | 3,960 | 0 |
| (1,1,4)√2 | 3,960 | 0 |
| (3,3)√2 | 220 | 0 |

**全部被至少一个现有向量挡住。**

### 2.3 连续覆盖半径量化（本轮新增，比“无空隙”更强）

把 604 个向量归一化到单位球面，寻找一个方向 `u` 使得对所有 `v` 都有 `⟨u,v⟩ ≤ 0.5`（即与所有向量夹角 ≥60°）。

- 100 万个随机方向：没有一个满足，最小 `max⟨u,v⟩ = 0.637`。
- 150 个多起点子梯度优化：最小 `max⟨u,v⟩ = 0.57765`，对应角度 **54.71°**。
- 追加 60 个起点：最小 **0.5794**，仍远高于 0.5。

**含义**：这 604 个 60° 球冠在数值上覆盖整个球面，任意方向（不只是格点）都会与某个向量夹角 <60°。因此**任何 norm、任何点阵的第 605 个向量都无法加到这套 604 配置上**。

### 2.4 换 norm²=72 的完整排查（本轮新增）

把 604 向量乘 `√2`（坐标 `(p,q) → (2q,p)`）得到 norm²=72 的骨架，再在 norm²=72 的完整点阵中找第 605 个向量。

过程中发现并修正了一个**采样器 bug**（很值得后来者注意）：

- 原 DP 表用 `s + w` 递推，采样却用 `s - w` 选择，两者不一致，导致生成的“随机”向量几乎全是单坐标向量；
- 修正为一致的 `s - w` 后，norm²=72 的点阵总解数为 **6,707,310,485,413,230**，采样才真正多样。

修正后的结果：

- 一般采样 100,000 个候选：**86 个**满足与 604 个骨架的内积 ≤36；
- 但这 86 个的 `Z[√2]` 范数是 `(72, b)`、`b = 2Σpq ≠ 0`，而骨架范数是 `(72, 0)`；验证器要求**所有向量范数完全相同**，因此它们全部非法；
- 专门采样 `Σpq=0` 的纯形式候选 200,000 个：合法向量 **0 个**。

**结论**：范数必须逐分量相同（不只是 `Σ(p²+2q²)` 相同）。这也是一个容易踩的坑：只检查平方长度会得到假阳性。

### 2.5 p001 小结

- 604 配置的球冠覆盖是数值上很强的证据；扩展第 605 个向量在任何 norm 下都不可行。
- 要突破必须**换一套完全不同的 604 子集**（从零构造 605），而不是在现有配置上加一个。
- 给后来者：`Σpq=0` 是必须检查的范数条件；DP 采样方向要一致。

## 3. p003 · Ramsey R(4,6) 下界

### 3.1 轻量编码（本轮新增，便于复用）

“给 35 点图加一个新顶点”只需决定新顶点的邻域 `N(v) ⊆ V`（35 个布尔变量）：

- 若 `N(v)` 内含三角形 → 新顶点参与 K4；
- 若 `V \ N(v)` 内含独立 5 集 → 新顶点参与 I6。

对基线图，三角形 383 个、独立 5 集 784 个，共 **1167 条 3/5 元子句、35 个变量**。

### 3.2 37 个 35 点图全部 UNSAT

取 McKay 的 `r46_35some.g6`（37 个 35 点 (4,6)-图），逐个用 CaDiCaL 求解：

- **37 个全部 UNSAT**，每个 <1 秒；
- 与本仓库已有结论（约 4.5 秒全部 UNSAT）一致，属于独立复核。

**意义**：任何 36 点 (4,6)-图删掉一个顶点都得到这 37 个图之一；若这 37 个是全部 35 点图，则该题无法靠“加一个顶点”突破。

### 3.3 复现

```bash
python3 src/codearts/p003/sat_all.py   # 需要 r46_35some.g6 与 python-sat
```

## 4. 远端大机器经验（对后来者最有用的一条）

本轮在 640 核 / 2 TB 内存 / 300 GB 磁盘的 Ubuntu 22.04 aarch64 环境上部署了 CP-SAT：

1. **远端没有 python3/pip/gcc**，`apt-get install python3-pip` 可能失败；可用 `get-pip.py` 或直接解压 pip wheel 到用户目录（不要写系统目录）。
2. **ortools 最新版没有 aarch64 wheel**，`pip install ortools` 会报 `from versions: none`；**必须指定 `ortools==9.11.4210`**（有 `cp310 + manylinux2014_aarch64`）。
3. 远端下载 26 MB 的 ortools 可能极慢；可在本地用
   `pip download ortools==9.11.4210 --platform manylinux2014_aarch64 --python-version 310 --implementation cp --abi cp310`
   下好全部依赖 wheels，再通过 SSH `tar | ssh` 传过去解压到 `PYTHONPATH` 目录。
4. SSH 直连授权只有 5 分钟；用 `ssh -M -S <sock> -N -f` 建立 ControlMaster（`ControlPersist=12h`）可复用。
5. 远端任务一律 `setsid + nohup`，并用看门狗脚本每 60–120 秒检查、崩溃自动重启；结果与日志落盘。
6. **CP-SAT 大模型的内存教训**：worker 数按内存给，不按核数给（7M 约束下 256 worker 必 OOM，64 稳定在 137 GB）。
